## 1. 提交序列与工作包

R0 可以按提交 1～5 独立落地。M1.6 是一次公开 Java API 替换；为了避免为“保持中间提交可编译”引入临时 v1/v2 双轨接口，Task 8～14 是同一个原子迁移提交中的工作包。执行过程中按工作包运行局部测试，只有四模块全绿后才形成提交 8。

| 序号 | 提交主题 | 结果 |
|---:|---|---|
| 1 | `docs: align specifications with R0 and M1.6 decisions` | 旧规范不再指挥实现过时契约 |
| 2 | `build: pin Java 21 and Maven toolchain` | Wrapper、Enforcer、插件版本固定 |
| 3 | `test: split unit and MySQL integration lifecycles` | IT 不再静默跳过 |
| 4 | `ci: add Java 21 unit and MySQL gates` | PR 有两个强制 job |
| 5 | `build: upgrade Spring Boot baseline to 4.1` | 框架进入当前支持线 |
| 6 | `test(core): add M1.6 contract characterization` | 旧行为与预期破坏点被固定 |
| 7 | `feat(core): introduce deterministic decision values` | 输入和值语义定版 |
| 8 | `refactor: freeze M1.6 core contracts and migrate adapters` | Task 8～14 原子完成，四模块全绿 |
| 9 | `docs: record R0 and M1.6 verification` | 规范、测试数和迁移说明同步 |

## 18. 中止条件

出现以下任一情况，停止进入下一 Task，先回到设计或新增 ADR：

- Boot 4.1 要求改变模块职责或公开 REST 协议；
- v1 JSON 存在无法无损判断的实际生产形态，超出本文迁移表；
- executor-owned plan 需要暴露 Spring Bean 或 Registry 到运行热路径；
- timeout 实现再次出现业务任务嵌套提交；
- 为兼容旧测试重新公开可写 ExecutionState；
- M1.6 需要修改数据库生命周期事务才能正确工作。

最后一项应移交 M2c，而不是在 M1.6 中顺手实现半套发布模型。
